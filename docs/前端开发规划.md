## 2. 当前前端与路由的已知不一致

主页是已经设计好的完整入口页，因此保留了多个未来功能入口。但当前路由只注册了主页、登录、注册和 404。

主页中目前存在但尚未恢复路由的入口：

| 入口 | 当前跳转 | 当前结果 | 处理策略 |
|------|----------|----------|----------|
| 顶部搜索框 | `/search?q=...` | 进入 404 | 等搜索页设计确认后恢复 `/search` |
| 活动卡片点击 | `/posters/:id` | 进入 404 | 等活动详情页设计确认后恢复 |
| “查看更多” | `/posters` | 进入 404 | 等活动列表页设计确认后恢复 |
| 左侧“我的活动” | `/dashboard` | 进入 404 | 等个人中心/看板设计确认后恢复 |
| 左侧“创建活动” | `/dashboard` | 进入 404 | 应改为未来的创建活动页或草稿中心 |
| 页脚“知识图谱” | `/knowledge` | 进入 404 | 等知识图谱页设计确认后恢复 |

短期原则：

- 不要因为主页已有入口就直接补页面代码。
- 每个入口必须先有页面设计文档，再恢复路由和实现页面。
- 若短期不实现入口，可在主页上临时禁用或给出“功能设计中”的提示，但不要接一个半成品页面。

## 3. 开发总原则

本项目采用“先文档，后页面”的前端开发方式。

必须遵守：

- 新页面实现前，先在 `docs/frontend-design/` 下补设计文档。
- 页面设计文档至少包含：目标、路由、权限、布局、状态、接口、mock、验收项。
- 页面实现优先单文件组件，复杂度明确上升后再拆组件。
- 不恢复未设计页面的路由。
- 不在 mock-server 中暴露已经删除且未设计的业务接口，避免误判功能已完成。
- 首页是当前唯一完整业务入口，改动首页前必须确认不会破坏既有视觉设计。

### 阶段 1：活动浏览闭环

目标：让主页上的活动入口不再断裂，形成“主页 -> 列表 -> 详情”的基础浏览闭环。

建议新增设计文档：

- `docs/frontend-design/POSTER_LIST_DESIGN.md`
- `docs/frontend-design/POSTER_DETAIL_DESIGN.md`

建议恢复页面：

| 路由 | 页面 | 优先级 |
|------|------|--------|
| `/posters` | 活动列表页 | 高 |
| `/posters/:id` | 活动详情页 | 高 |

依赖接口：

| 用途 | 接口 |
|------|------|
| 活动列表 | `GET /api/posters?q=&status=&page=&per_page=` |
| 活动详情 | `GET /api/posters/{id}` |
| 关联活动 | `GET /api/posters/{id}/related` |
| 日历导出 | `GET /api/posters/{id}/ics` |

实现范围：

- 活动列表只做浏览、搜索、状态/类型基础筛选。
- 活动详情只做展示和返回，不做编辑、审核、AI 增强。
- 权限上普通登录用户可访问；未登录时按后端实际策略决定是否跳登录。

不做内容：

- 不做创建活动。
- 不做审核。
- 不做批量操作。
- 不做数据源管理。

### 阶段 2：搜索页

目标：恢复主页顶部搜索框的目标页，只做内部搜索。

已有设计文档：

- `docs/frontend-design/SEARCH_DESIGN.md`

建议恢复页面：

| 路由 | 页面 | 优先级 |
|------|------|--------|
| `/search` | 内部搜索页 | 高 |

依赖接口：

| 用途 | 接口 |
|------|------|
| 内部搜索 | `GET /api/search/internal?q=...` |

实现范围：

- 结果只包含活动海报和知识节点。

- 不做 LLM 搜索。
- 不做搜索结果入库。

## 8. 权限规划

角色约定：

| 角色 | 能力 |
|------|------|
| visitor | 访问主页、登录、注册；是否可看活动列表需按产品决定 |
| viewer | 浏览活动、搜索、知识节点、个人日历 |
| publisher | viewer 能力 + 创建/编辑/提交活动 |
| admin | 全部能力 + 审核、数据源、审计、导出、AI 工具 |

前端实现建议：

- 路由 `meta.requiresAuth` 控制是否登录。
- 路由 `meta.role` 控制最低角色。
- 不要只靠前端隐藏按钮，后端仍必须校验权限。
- 当前阶段路由守卫只处理登录/注册页重定向，后续恢复业务页时再扩展。

## 9. 当前优先级建议

最推荐的下一步顺序：

1. 修正主页未开放入口策略：决定 `/search`、`/posters`、`/dashboard` 等入口是禁用、提示，还是按阶段恢复。
2. 先实现活动列表页和活动详情页，因为主页已有大量活动卡片入口。
3. 再实现内部搜索页，因为主页顶部搜索已经是核心入口。
4. 再实现发布者的创建/编辑/我的活动。
5. 最后做管理端和 AI/爬虫能力。

原因：

- 活动浏览闭环是用户最容易理解和验收的核心功能。
- 搜索页依赖活动详情和知识节点详情的跳转目标，最好不要孤立实现。
- 管理端能力复杂，应该等基础浏览和发布流程稳定后再做。

## 10. 验收与质量要求

每个阶段完成后至少执行：

- `npm.cmd run build`
- 页面手动验收：正常态、空状态、加载态、错误态
- 路由验收：刷新页面、直接访问 URL、非法路径
- 登录态验收：未登录、已登录、退出登录
- mock 联调：mock-server 与真实后端字段一致
- 文档回写：实现与设计不一致时更新对应设计文档

## 11. 明确暂不做的内容

当前规划不建议立即开发：

- 外部搜索。
- LLM 驱动搜索。
- MCP 工具调用 UI。
- 批量审核和复杂合并流程。
- 数据源爬虫配置界面。
- 导出中心。
- 大规模组件库抽象。

这些能力后端已有基础，但前端应等核心浏览、搜索、发布流程稳定后再逐步接入。
