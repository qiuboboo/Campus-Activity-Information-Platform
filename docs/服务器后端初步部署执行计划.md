# 服务器后端初步部署执行计划

本文用于指导在服务器上完成“校园活动信息平台”后端的第一阶段部署，目标是让另一位执行者可以直接按文档逐步操作，在尽量少做额外决策的前提下，把当前仓库中的后端服务部署到服务器上并完成基础验证。

本文默认执行者在服务器上以 `workspace` 用户进行项目开发和运行，以 `root` 用户处理系统级安装与配置。

## 1. 目标

本次部署目标不是一次性完成生产级上线，而是完成“初步部署”，具体包括：

- 将项目代码放置到服务器开发目录
- 为 `workspace` 用户准备可用开发环境
- 准备 Python 虚拟环境并安装后端依赖
- 准备 `.env` 配置
- 用本地 Python 方式启动后端并验证接口
- 用 Docker 方式启动后端并验证接口
- 确认后续可继续接入 Nginx、域名、HTTPS 与数据库扩展

## 2. 当前约束与已知前提

结合当前服务器和仓库状态，执行时按以下假设处理：

- 服务器系统：`Ubuntu 22.04`
- 开发用户：`workspace`
- 管理用户：`root`
- Docker 已安装可用
- 项目仓库中已包含：
  - `backend/`
  - `deploy/nginx/campus-activity.conf`
  - `docs/`
- 当前后端第一版默认可以先使用 `SQLite`
- 当前后端尚未要求必须接入 `PostgreSQL / Redis / Nginx`

## 3. 本次部署的建议策略

本次部署建议采用“双验证路径”：

1. 先用 `Python 虚拟环境 + python wsgi.py` 跑通
2. 再用 `Docker Compose` 跑通

原因：

- Python 直跑更容易排查代码与依赖问题
- Docker 方式更接近后续部署形态
- 两条路径都通过后，后端基础可认为稳定

## 4. 执行角色分工

### 4.1 root 负责

- 安装系统级软件
- 检查和修复 Docker
- 调整目录权限
- 必要时开放端口

### 4.2 workspace 负责

- 拉取或同步仓库代码
- 创建虚拟环境
- 安装 Python 依赖
- 配置 `.env`
- 运行后端服务
- 执行接口验证

## 5. 执行前检查清单

在正式部署前，先确认以下项目。

### 5.1 用户与目录

以 `root` 检查：

```bash
id workspace
ls -la /home/workspace
```

预期：

- `workspace` 用户存在
- `/home/workspace` 可用

### 5.2 Docker 状态

```bash
docker --version
docker ps
```

预期：

- Docker 命令可执行
- `docker ps` 无报错

### 5.3 Python 状态

```bash
python3 --version
pip3 --version
```

预期：

- Python 3 可用
- pip3 可用

### 5.4 Git 状态

```bash
git --version
```

预期：

- Git 可用

## 6. 阶段一：准备项目目录

### 6.1 目标

确保项目代码位于 `workspace` 的家目录下，且归属正确。

### 6.2 执行步骤

如果项目目录已经在 `/home/workspace/校园活动平台`，先检查权限：

```bash
sudo chown -R workspace:workspace /home/workspace/校园活动平台
```

如果项目还在 `root` 目录下，则复制过去：

```bash
sudo cp -r /root/校园活动平台 /home/workspace/
sudo chown -R workspace:workspace /home/workspace/校园活动平台
```

### 6.3 验收标准

```bash
ls -la /home/workspace/校园活动平台
```

应能看到：

- `backend/`
- `deploy/`
- `docs/`
- 根目录 `README.md`

## 7. 阶段二：准备 workspace 开发环境

### 7.1 目标

确保 `workspace` 用户可独立完成后端开发与运行，不依赖 `root` 私有工具路径。

### 7.2 执行步骤

切换用户：

```bash
su - workspace
```

确认当前用户：

```bash
whoami
echo $HOME
```

预期：

- `whoami` 为 `workspace`
- `HOME` 为 `/home/workspace`

### 7.3 Node 与 Claude Code

如果执行者还需要在服务器上使用 Claude Code 或其他 Node 工具，则继续确认：

```bash
command -v nvm
node -v
npm -v
```

要求：

- 若要使用 Claude Code，则 Node 版本应至少为 `18+`
- 不允许继续依赖 `/root/.nvm/...`

说明：

这一步不是本次 Flask 后端部署的硬前置，但如果执行者依赖大模型在服务器协助操作，则应先确保 `workspace` 用户下的 Node 与 Claude Code 可用。

## 8. 阶段三：准备 Python 虚拟环境

### 8.1 目标

在 `workspace` 用户下创建独立 Python 环境，避免污染系统 Python。

### 8.2 执行步骤

```bash
cd /home/workspace/校园活动平台/backend
python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
```

### 8.3 验收标准

```bash
python --version
pip list
```

预期：

- 当前 Python 来自 `.venv`
- 能看到 Flask 等依赖已安装

### 8.4 失败处理

如果 `pip install -r requirements.txt` 失败，应优先记录：

- 失败的包名
- 完整报错
- 是否为网络超时
- 是否为编译依赖缺失

处理原则：

- 不要先盲目换框架
- 优先补系统依赖或重试安装

## 9. 阶段四：准备环境变量

### 9.1 目标

复制项目示例配置，并以“本地可运行优先”的原则完成第一版配置。

### 9.2 执行步骤

```bash
cd /home/workspace/校园活动平台/backend
cp .env.example .env
```

然后检查 `.env`，建议第一版保留以下设置：

```env
FLASK_ENV=development
AUTO_CREATE_TABLES=true
DATABASE_URL=sqlite:///app.db
JWT_SECRET_KEY=replace-with-a-random-secret
DEFAULT_ADMIN_USERNAME=admin
DEFAULT_ADMIN_PASSWORD=admin123456
POSTERS_PER_PAGE=10
REDIS_URL=redis://localhost:6379/0
OPENCLAW_BASE_URL=
EMBEDDING_ENABLED=false
```

### 9.3 当前阶段原则

本次部署阶段：

- 不要求真实 PostgreSQL
- 不要求真实 Redis
- 不要求 OpenClaw

先让最小后端成功运行。

## 10. 阶段五：用 Python 方式启动后端

### 10.1 目标

不依赖 Docker，先验证代码本身可以运行。

### 10.2 执行步骤

```bash
cd /home/workspace/校园活动平台/backend
source .venv/bin/activate
python wsgi.py
```

### 10.3 预期结果

应能看到 Flask 启动日志，监听：

```text
0.0.0.0:5000
```

### 10.4 验证方式

另开一个终端，执行：

```bash
curl http://127.0.0.1:5000/api/health
```

应返回类似：

```json
{
  "status": "ok"
}
```

### 10.5 再验证登录接口

```bash
curl -X POST http://127.0.0.1:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123456"}'
```

预期：

- 返回 token
- 返回默认管理员信息

### 10.6 失败处理

如果 Flask 启动失败，优先检查：

- `.env` 是否存在
- 依赖是否安装完整
- 端口是否被占用
- `sqlite:///app.db` 是否可写

## 11. 阶段六：用 Docker 方式启动后端

### 11.1 目标

验证仓库中当前 Docker 入口可以正常工作。

### 11.2 注意事项

当前仓库中的 `docker-compose.yml` 包含：

- `api`
- `postgres`
- `redis`

而 `.env.example` 默认是 `sqlite:///app.db`。因此在执行 Docker 前，必须先明确一种策略：

### 11.3 推荐策略

当前第一阶段建议：

- 先只验证 `api` 容器能否正常 build
- 若要联动 `postgres`，需手动把 `DATABASE_URL` 改为容器内 PostgreSQL 地址

推荐在 Docker 场景下将 `.env` 临时改为：

```env
DATABASE_URL=postgresql+psycopg://campus:campus123456@postgres:5432/campus_activity
```

### 11.4 执行步骤

```bash
cd /home/workspace/校园活动平台/backend
docker compose up -d --build
```

### 11.5 验证方式

```bash
docker compose ps
docker compose logs --tail=100 api
```

预期：

- `api`、`postgres`、`redis` 启动成功
- `api` 无持续崩溃重启

然后验证：

```bash
curl http://127.0.0.1:5000/api/health
```

### 11.6 失败处理

如果失败，优先检查：

- `DATABASE_URL` 是否已改为 PostgreSQL 版本
- `postgres` 容器是否正常
- `api` 是否因数据库连接失败退出

## 12. 阶段七：对外访问准备

### 12.1 当前目标

只做最小暴露，不立即上生产。

### 12.2 可选动作

如果需要从外网直接访问 Flask 接口，先检查服务器安全组或防火墙是否放行：

- `22`
- `5000`

### 12.3 验证方式

在服务器外部访问：

```text
http://<server-ip>:5000/api/health
```

说明：

若只是内部调试，可先不开放公网 5000，等后续接 Nginx 后再开放 `80/443`。

## 13. 阶段八：记录结果

执行完成后，应记录以下结果，方便继续交接：

- Python 方式是否启动成功
- Docker 方式是否启动成功
- `.env` 当前使用的是 SQLite 还是 PostgreSQL
- 登录接口是否可用
- 是否已经开放 5000 端口
- 当前项目目录绝对路径
- 当前建议的后续任务

建议执行者最终输出一份简短部署结果摘要，例如：

```text
1. 项目已部署到 /home/workspace/校园活动平台
2. Python 直跑成功 / 失败
3. Docker Compose 成功 / 失败
4. 健康检查接口成功 / 失败
5. 当前数据库模式：SQLite / PostgreSQL
6. 建议下一步：接 Nginx / 补日志 / 接前端
```

## 14. 建议执行顺序

严格按以下顺序执行，不建议跳步：

1. 检查用户、Python、Git、Docker
2. 准备项目目录与权限
3. 切换到 `workspace`
4. 建立 Python 虚拟环境
5. 安装依赖
6. 配置 `.env`
7. 跑通 `python wsgi.py`
8. 验证 `/api/health`
9. 验证 `/api/auth/login`
10. 再尝试 `docker compose up -d --build`
11. 记录结果

## 15. 暂不做的事

本次初步部署阶段，以下内容明确不作为强制目标：

- 完整 Nginx 上线
- HTTPS 证书接入
- 域名绑定
- 生产级 systemd 守护
- PostgreSQL 数据备份策略
- Redis 持久化策略
- OpenClaw 接入
- 前端正式联调

这些内容应在“后续部署增强阶段”再处理。

## 16. 给执行模型的注意事项

如果把本计划交给另一个模型执行，应要求其遵守以下原则：

- 默认使用 `workspace` 用户执行开发相关操作
- 不要把开发工具继续安装到 `/root/.nvm/...`
- 优先保证“后端先跑起来”，不要过早扩展范围
- 每完成一个阶段，都要先验证再进入下一步
- 如果命令失败，先记录报错，再分析，不要直接跳到重装系统
